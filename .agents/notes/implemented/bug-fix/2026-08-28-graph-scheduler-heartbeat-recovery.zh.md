# Agent Note: 调度器心跳恢复保留节点尝试预算

Status: implemented

[English](2026-08-28-graph-scheduler-heartbeat-recovery.md) | 中文

## 问题

临时调度器心跳失败会立即撤销运行权限，即使租约仍有续期时间。恢复还会在对账 Worker 和协作引用之前统计全部已记录尝试，包括被父级调度器取消的未完成尝试。因此，反复发生的 Host 级中断可能在没有任何已完成 Worker 结果时耗尽节点预算，并让 `awaiting_user` 缺少持久检查点。

## 决策

当前租约仍然存活时，Graph Mode 会重试心跳失败。`GraphSchedulerAuthorityError` 标识已经被 fencing 或已经过期的租约，并立即撤销写权限；瞬时重试未成功且租约到期时也执行相同处理。

恢复会在评估节点预算之前对账外部引用。带有 `finishedAt` 的尝试会消耗预算；未完成尝试保留在已取代 Generation 的审计记录中，但会从恢复后 Generation 的活动尝试列表中移除。不安全和真正耗尽的节点会获得包含恢复判定的持久 `awaiting_user` 检查点。Web 执行视图会为该状态提供节点重试，并在恢复检查点不能安全地原样继续时隐藏批准操作。

SQLite Scheduler 默认提供 120 秒的运行租约，并最多等待 30 秒的事务争用。心跳间隔仍由 Graph Mode 独立配置。

## 考虑过的替代方案

- **第一次心跳异常就失败** — 未采用，因为临时 SQLite 争用、较长的 JavaScript 暂停或传输中断本身不能证明另一个 Owner 已经 fencing 当前租约。
- **统计每个已启动尝试** — 未采用，因为 Host 权限丢失导致的父级取消不是已结算的 Worker 结果，反复的基础设施恢复不应消耗任务策略。
- **恢复时重置全部尝试** — 未采用，因为已完成失败属于任务证据，并且必须继续执行不可变节点上限。
- **自动重新派发所有不确定副作用** — 未采用，因为手动和未对账副作用可能重复外部变更；它们需要检查点和明确的操作员决定。

## 后果

- 瞬时心跳失败在接管成为可能之前拥有多次有界续期机会。
- 被 fencing 的 Owner 仍会立即停止持久写入。
- 已恢复的幂等工作不会仅因父级调度器中断而损失任务尝试次数。
- 恢复判定通过持久操作与检查点证据变得可见且可操作。
- 精确心跳异常仅在同一进程内恢复时保留；Host 重启后，恢复会报告持久租约和外部对账证据，因为已被 fencing 的 Session Writer 不能追加失败心跳。
