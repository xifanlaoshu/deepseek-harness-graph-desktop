# Agent Note: 渐进式任务图规划检查点

Status: proposed

[English](2026-08-18-progressive-graph-planning-checkpoints.md) | 中文

## 问题

Graph 控制器目前根据用户请求和静态角色摘要提交完整的执行 DAG。它无法利用自身 worker 随后发现的分析、架构和仓库脚手架证据进行规划，也无法获知 worker 实际解析出的模型容量或观察到的执行限制。因此，一个宽泛的实现节点可能同时包含互不相关的子系统，在没有产出文件的情况下耗尽一次模型响应和全部重试次数。

把架构节点重新连接到控制器节点会让持久任务图形成环，并把控制器当作普通委派任务。要求用户识别并拆分过大的节点，也会把 Graph Mode 应当承担的编排责任转移给用户。

## 提案

Graph Mode 将通过持久规划检查点支持渐进式规划。控制器位于任务 DAG 之外，充当会话的控制平面。检查点把控制权交还给控制器，但不会向不可变任务图修订加入反向边或可执行谓词。

对于实现方式取决于仓库事实的工作，控制器将首先提交只包含必要需求分析、仓库或脚手架检查以及架构节点的发现修订。该修订将在这些节点之后声明一个扩展检查点。检查点具备执行资格后，调度器将停止准入尚未发现的执行工作，持久化暂停运行和检查点证据，并通过一条模型可见且已记录的消息唤醒控制器。

检查点规划上下文将包含有界的结构化节点输出和产物引用、仓库或脚手架摘要、会话自有的角色选择、精确的提供方或模型调度限制，以及由 LLM 服务解析的模型元数据，包括已知的上下文窗口、输出限制和推理选择值。未知能力将明确保持未知，而不会获得虚构值。随部署变化的节点规模和规划限制将成为经过校验的 Graph 设置，而不是插件常量。

控制器将利用这些证据提交下一个不可变修订。除非输入发生变化，已经完成的发现节点将携带来源信息复用；该修订会按照分配模型的能力和文件所有权，以合适颗粒度展开实现、集成、评审、验证和文档节点。常规修订失效规则会重新执行所有受影响的后继节点，同时保留旧修订和旧运行供检查。

任务图提交在修订写入日志之前包含一次规划校验。校验会拒绝可写路径所有权冲突、缺少验证、超出已配置策略而合并多个可独立验证子系统的执行节点，以及超过声明容量的模型分配。拒绝结果将向控制器返回结构化发现，使其无需要求用户拆分工作即可重新提交。

检查点模式将区分初始扩展、结构化评审或验证拒绝后的修复，以及运行限制后的重新规划。带有有效产物的 `max-tokens` 结果可以在有界继续策略内延续同一个 worker 会话；只有推理内容或多次没有有效进展的尝试将返回控制器拆分节点，而不是重新启动相同的一次性任务。提供方或进程故障保留独立的有界重试策略。

评审和验证分支将发布机器可读的判定和问题归属。拒绝结果会暂停受影响工作，并让控制器创建包含定向修复节点的新修订；任务图本身继续保持无环，修订节点的传递后继节点依据现有失效规则重新执行。

检查点 payload 携带精简输出和产物引用，而不是完整子会话 transcript。子会话仍是详细消息和工具活动的权威记录，LoopX 只接收现有的有界协调 observation 和结算证据。控制器尚未展开到可执行修订中的工作不会创建 todo。

Graph UI 将展示检查点状态、控制器产生的扩展或修复修订、复用的发现证据以及导致暂停的规划原因。独立的设计与执行展示由[任务图双视图决策](../../implemented/feature/2026-08-18-dual-graph-design-and-execution-views.zh.md)负责；本提案提供该展示所消费的修订和检查点证据。

角色和规划设置将写入会话自有 Graph 配置的快照。全局角色模板或模型目录变更只影响后续会话或显式会话更新，绝不会静默重新解释现有任务图的规划证据。

## 考虑过的替代方案

**在任何 worker 运行前生成完整 DAG。** 这种方式让一次控制器轮次保持简单，却迫使实现颗粒度在分析、架构和仓库检查结果出现之前依靠猜测确定。

**把控制器表示成带反向边的任务图节点。** 这种方式把重新规划显示成普通工作，但会引入环、混合控制权限与委派执行，也让不可变修订无法指出哪次控制器决策产生了某个节点。

**每个节点结束后都唤醒控制器。** 持续重新规划可以观察最新证据，却会串行化独立工作、增加控制器成本并使修订历史产生噪声。明确的不确定性和决策检查点可以保留有效并行。

**只依赖更强的控制器提示词。** 提示词指导可以改善典型任务图，却无法观察缺失的模型元数据、强制执行可写路径所有权或阻止格式有效但规模过大的提交。控制器需要结构化规划上下文和确定性校验。

## 验收标准

- 控制器可以提交只包含发现工作的修订，并在选定的分析、仓库检查和架构节点之后声明持久扩展检查点。
- 具备执行资格的检查点会暂停尚未发现的执行工作，持久化原因和证据，并在不添加任务图环或控制器任务节点的情况下唤醒控制器。
- 已记录的规划上下文包含有界前置结果、产物引用、仓库或脚手架证据、会话角色选择、调度限制以及 LLM 服务能够解析的全部模型能力；未知值继续保持未知。
- 控制器可以通过新的不可变修订展开同一任务图，携带来源信息复用未改变的发现节点，并创建适合模型能力的执行节点。
- 提交校验在记录修订之前，针对已配置的节点规模违规、可写路径冲突、缺少验证和不兼容模型分配返回控制器可见的结构化发现。
- 评审或验证拒绝会创建控制器检查点，其替换修订将重新执行每个变更节点及其完整的传递后继闭包。
- 运行限制处理会区分同会话继续、控制器重新规划和提供方重试；`max-tokens` 尝试不会盲目重复同一个一次性提示词直到耗尽 `maxAttempts`。
- 扩展后仍对跨角色的精确模型执行准入限制，因此分配给同一本地模型的多个角色不会超过该模型配置的并行度。
- 重启和历史回放无需读取当前全局模板，即可重建暂停检查点、规划证据、其产生的修订以及复用节点来源。
- 组装后的 Web 应用提供面向产品的覆盖，验证发现、检查点暂停、控制器展开、执行、拒绝驱动的修复以及所得设计和执行修订的检查。

## 风险

渐进式规划会产生更多修订和控制器轮次，因此检查点位置必须明确且稀疏。模型元数据可能缺失或不准确，即使路由声明了容量，输出大小仍取决于模型；保守且可配置的策略和观察到的运行证据可以辅助规划，但不能声称能够确定预测 token。若 worker 发布冗长结果，检查点 payload 本身也会消耗上下文，因此 schema 和大小限制必须约束摘要，并把完整证据留在子会话中。在暂停期间发生崩溃时，需要持久检查点准入状态来避免重复唤醒控制器。只有在现有失效规则判定直接变更和入向依赖均未变化时，跨修订复用发现结果才是安全的。
