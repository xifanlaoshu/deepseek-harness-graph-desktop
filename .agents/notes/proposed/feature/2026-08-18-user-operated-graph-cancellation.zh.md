# Agent Note: 用户控制的 Graph 取消操作

Status: proposed

[English](2026-08-18-user-operated-graph-cancellation.md) | 中文

## 问题

Graph 调度器在控制器轮次之外运行。因此，父会话输入框的 Stop 操作只负责控制器的当前轮次，Graph 创建的一次性 subagent 会话保持只读，而 `/graph off` 只改变后续输入路由，不会停止活动运行。用户无法在不替换任务图修订或关闭 Host 的情况下，停止单个卡住或成本过高的 worker，也无法取消整次运行。

Graph Mode 已经会在新修订取代旧运行或插件 dispose（资源释放）时中止工作，但没有提供由用户指定目标的控制操作。脱离 Graph 所有权直接复用子会话中断，还会把中断报告为一次尝试失败；重试策略可能立即创建另一个 worker，从而违背用户意图。

## 提案

Graph Mode 将提供一项由 Host 归属的控制操作，供 Graph 面板、Graph 创建的子会话视图、人工命令路径和控制器工具共同使用。每个请求都必须指定父会话、任务图 id、修订和运行 id。节点请求还必须携带节点 id、尝试 id 和已观察到的尝试状态，避免陈旧页面取消更新后的工作。

该操作支持 `cancel-run` 和 `cancel-node`。`cancel-run` 会中止所有活动尝试，阻止排队或等待中的节点启动，把所有非终态节点标记为已取消，并以已取消状态结束运行。`cancel-node` 只中止指定的活动尝试，把该节点标记为由用户取消，按照现有依赖规则处理其后继，并允许独立分支完成。必需后继会被取消，输入条件未满足的条件后继会被跳过，其余独立工作结算后，运行以已取消状态结束。

控制器只能在把明确的人工请求分类为 `control` 后调用同一操作；普通需求调整仍会创建任务图修订。取消操作本身绝不创建替代任务图，也不会自动重试工作。后续重试、修复或重新规划必须由另一条明确的用户输入触发，并创建新的不可变修订，使被取消的运行继续可供检查。

## 取消操作的所有权与证据

Graph Mode 负责中止子会话、释放准入许可、改变节点与运行阶段以及结算外部协调，而不是把这些职责交给通用会话运行时。被取消的尝试会记录独立的用户取消结果，以及取消时间、入口和可选的公开安全原因。它不会重新进入 `ready`，不会进入自动失败重试路径，也不会根据 `maxAttempts` 再次排入 worker。

如果尝试已经认领 LoopX 工作，Graph Mode 会使用生命周期长于 worker 中止操作的终态结算信号，写入不可执行的 blocker 证据。控制操作只有在子会话释放、准入许可归还、终态运行快照写入并尝试完成协调结算后才返回成功。结算失败仍作为持久证据保留，绝不会使被取消节点重新变为可执行状态。

取消与完成可能发生竞争。系统以首个被接受的终态转换为准：完成先发生时，迟到的取消请求返回“目标已终止”，且不得覆盖已完成输出；取消先被接受时，迟到的子会话结果不得恢复该尝试。重复提交同一目标操作必须保持幂等。

会话事件流将保留控制请求及其产生的运行快照。因此，Graph 投影、导出的会话和回放都能显示取消的发起主体、时间、指定尝试和任何 LoopX 结算错误，而不依赖进程内中止状态。

## 浏览器控制

Graph 面板的活动运行标题栏将提供需要确认的“停止运行”操作，并显示运行标识和活动尝试数量。运行中的执行节点将在[双任务图设计与执行视图决策](../../implemented/feature/2026-08-18-dual-graph-design-and-execution-views.zh.md)所述的节点弹窗中提供“取消节点”。请求开始后，按钮立即禁用，并以权威投影结果完成状态更新，不使用乐观本地状态。

Graph 创建的一次性子会话仍保持 transcript（文本记录）只读，但当精确对应的父运行和尝试仍处于活动状态时，其标题栏会显示“取消节点”。该操作将指定父 Graph 控制操作，不会调用通用 `session.cancel`，也不会伪装成一次性子会话可以接收后续消息。普通可继续 subagent 的 Stop 行为保持不变。

## 考虑过的替代方案

**从两个页面调用通用会话取消。** 这种方式可以停止模型请求，但会绕过 Graph 对重试、准入许可、运行阶段、后继结果和 LoopX 结算的所有权。

**把 `/graph off` 视为取消。** 模式启用状态控制后续人工输入的路由。把它与执行取消绑定，会让设置操作以破坏性方式停止工作，而且仍然不能提供节点级操作。

**提交空修订或替代修订来停止工作。** 修订替换已经会中止旧运行，但它还会启动新工作、要求控制器参与，并在用户只请求执行控制时记录设计变更。

**把已停止的子会话映射为普通尝试失败。** 现有重试策略可能立即启动另一个子会话。用户取消需要独立的终态原因来禁止自动重试。

## 验收标准

- 用户可以从父会话的 Graph 面板取消活动 Graph 运行，无需重启 Host 或提交替代修订。
- 用户可以从执行证据抽屉和 Graph 创建的子会话页面取消精确对应的运行中节点。
- 所有入口都调用同一项由 Graph 归属、目标精确且幂等的控制操作；操作会报告陈旧或已终止目标，且不会影响更新后的尝试。
- 运行取消会阻止所有非终态节点再次启动，并记录一个终态为已取消的运行。
- 节点取消只停止指定尝试，通过现有依赖规则记录持久的后继结果，并允许独立分支完成结算。
- 无论 `maxAttempts` 还剩多少次，用户取消都具有独立的记录原因，而且绝不会进入自动失败重试路径。
- 完成与取消发生竞争时，只保留一个终态结果；完成先获胜时，系统绝不会替换成功输出。
- 每个已认领的 LoopX 工作项都会在取消完成前尝试写入终态 blocker 结算；结算失败会保留在持久 Graph 证据中。
- 回放、导出、Graph 投影和子会话链接都会保留取消来源、时间、目标以及最终节点和运行阶段。
- 面向用户的覆盖通过组装后的 Web 应用验证运行取消、两个浏览器界面的节点取消、陈旧控件、完成竞争、重试禁止、依赖节点结果、独立分支和 LoopX 补偿。

## 风险

取消无法撤销子会话已经完成的文件系统写入、子进程副作用或外部变更，因此 UI 必须说明该操作停止后续执行，而不是撤销已发生的影响。无响应的提供方或 LoopX 写回失败可能延迟完整结算，系统必须进入有长度上限的错误状态，不能报告虚假成功。持久控制事件和指定目标的 Host 操作会增加 schema 与授权范围；陈旧子会话页面、控制器误判和重复操作不得获得控制更新运行的权限。
