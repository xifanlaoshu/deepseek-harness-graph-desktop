# `@deepseek-ai/dsh-graph-mode`

English | [中文](README.zh.md)

For new work and revisions, `graph_submit` accepts an optional lineage decision with `new_task`, `analysis_refactor`, or `execution_correction`, a concrete title, trigger source, summary, referenced Run or node, error evidence, and success criteria. Graph Mode validates those references and classifications, derives the logical-task identity, parent or cross-Batch relationships, and exact added, changed, removed, preserved, and invalidated nodes, then stores the complete record with the provisional submission. When the controller omits the decision, the Host derives a conservative classification from accepted checkpoint, control, and terminal Run evidence; it never lets the model author runtime metrics.

`dsh-graph-mode` installs the `/graph` command, a controller-only system policy, the `graph_submit` tool, and a background DAG scheduler. `/graph` activates the mode for the current session; `/graph off` leaves it. Text after `/graph` is steered into the first controller step.

While active, each human input is classified as `new`, `revise`, `inspect`, `control`, `clarify`, or `direct`. New work and revisions submit a semantic graph draft without identity fields. For new work, Graph Mode derives a safe graph id from the objective and represented user input, adds a suffix when that id already exists, and assigns revision one. A revision binds to the current graph, receives the next revision and parent, and derives directly changed nodes from the accepted structures. The controller may declare relative workspace ownership; Graph Mode derives the physical allocation and resolves the timestamp, ordinary output schemas, node attempt and weight defaults, empty edge and branch-group lists, and termination limits from the frozen session and Provider configuration before it validates and stores the complete immutable revision. Revisions invalidate every transitive successor of the derived changes. Successful unaffected nodes reuse their published output with explicit provenance. Earlier graph revisions and run evidence remain unchanged.

Long ordered work starts a Campaign by submitting an initial Batch plan with the first Batch Graph. That submission sets `campaign.batchId` exactly to `campaign.plan.batches[0].id`. Each accepted Batch is a separate graph identity containing only that batch's work. Terminal settlement updates the Campaign from durable Run and Settlement evidence and sends a `graph-batch-complete` follow-up naming the next ready Batch. The controller creates an already registered Batch as a new graph with `intent=new` and only the named `campaign.batchId`; it omits `campaign.plan` and receives compact predecessor summaries and evidence ids in its worker context. When accepted analysis discovers work after every registered Batch is accepted, the controller may include `campaign.planExtension` while starting its first new Batch. Graph Mode appends that complete ordered suffix atomically, derives its source Run and Settlement evidence, and retains the submission reason as the next plan revision. It rejects extension while registered work remains, duplicate or non-tail Batch definitions, and any attempt to resend or alter the accepted prefix. A failed Batch is repaired through ordinary Revisions of that Batch Graph; replacement admission waits for the prior Run to become quiescent and retains its accepted Campaign execution before appending the new one. Already approved Batch Graphs are never regenerated.

Revision admission uses a recoverable `graph/submission` record. Graph Mode flushes the pending candidate before Scheduler acquisition or coordination preparation and publishes the Revision/Run pair only after ownership succeeds. Startup recovery can resume a pending submission only after its original in-process activation has left the single-flight set, while a busy or failed acquisition records a failed submission without moving the current Head. Resource reservation, coordination claim, running attempt, staged output, artifact integration, cancellation, and external settlement each cross an explicit session flush barrier before the corresponding external mutation. Every Scheduler lease has one handoff to its background execution; a failure before that handoff releases the lease. A failure after local admission but before Worker dispatch terminally settles an acquired coordination claim, reports an acquired model reservation as released, and returns the local permit. `externalOperationTimeoutMs` bounds cleanup and settlement at the caller even when a Provider does not settle after its signal aborts.

The scheduler runs outside the controller tool call, so the conversation remains interactive. A node becomes ready after its predecessors settle. Every incoming conditional edge must be active; a node whose conditional inputs do not all pass is skipped. Failed required predecessors cancel dependent work. Before publishing a terminal run snapshot, the scheduler aborts and drains every active node attempt, then closes that scheduler execution's node-update path; a late Worker-monitor callback cannot reopen the run, and a replacement Revision reads only the quiescent predecessor snapshot. Completed runs enqueue a logged `graph-run-complete` follow-up for controller synthesis. A failed follow-up includes the durable run error code, message, and node id so the controller reports the recorded cause instead of inferring one from partial node summaries.

Host prerequisites use immutable `environment` nodes rather than widening an engineer child. The controller first prefers repository-local wrappers and existing toolchains; when Maven installation, Docker changes, network acquisition, or another admitted host operation is necessary, it declares exact ordered commands, capabilities, sandbox mode, verification criteria, and documentary rollback commands. Graph Mode admits the plan only when `environmentEnabled`, `environmentCapabilities`, and `environmentDangerFullAccess` allow it, then stops at an `environment` checkpoint whose reason contains the complete stable JSON plan. The controller presents that checkpoint and waits; it must not revise the graph, execute the command, or infer approval. Approval authorizes only the next generation. Rejection cancels the run.

After approval, Graph Mode executes each recorded command directly through `ctx.shell`; no model child receives `danger-full-access` or an open-ended shell turn. Every command has a stable external reference and `environment` Settlement, and the parent log records its exit, signal, timeout, truncation, sandbox, and byte-count facts without retaining stdout or stderr text. Commands must refer to Host-managed environment variables or credential references instead of embedding secret values because the exact plan is logged. A command failure terminates the node without retrying the effect. A lost or conflicting terminal observation requires manual reconciliation, and a rollback command is never automatic: it must appear in a separately approved environment node. The deployment must mount a Shell Provider, and operating-system elevation, package-manager prompts, Docker daemon availability, and command portability remain Host responsibilities.

User-facing Web work ends with a verification node assigned to the `browser-tester` role when that role is enabled. The controller provides the exact target origin, critical flows, viewport and locale assumptions, and measurable DOM and visual assertions after the integrated runnable build. A user-supplied reachable target is an existing test environment, not a reason to schedule a speculative environment mutation. The browser worker keeps one explicit page id, prefers page snapshots and element identifiers for interaction, captures visual evidence when its model route accepts images, and inspects relevant console errors and failed network requests before publishing a structured decision. The worker never enters real secrets, performs destructive production actions, or closes another worker's page.

`graph_submit` accepts the documented semantic draft and rejects unknown nested fields with their precise paths. Admission reports independent role, node, acceptance, attempt, dependency, branch-group, and workspace errors together and includes a corrected minimal draft. A workspace draft may omit `readRoots`, which resolves to `["."]`, and `cleanup`, which resolves to the selected mode's default; empty, absolute, backslash-separated, unnormalized, or duplicate roots are rejected at the exact field path before durable graph validation. Concurrent implementation, documentation, integration, or specialist nodes must declare explicit, disjoint relative `workspace.writeRoots`; overlapping roots and missing parallel ownership fail before LoopX claims. The controller never submits graph ids, revision numbers, parent revisions, timestamps, changed-node lists, termination fields, Worker allocation ids, or absolute workspace paths and never has to reproduce deployment defaults or Provider capabilities. Host-owned fields and malformed graph-id hints from a controller call cannot override current session identity or policy. Review and verification drafts compose any specialized result schema with Host-owned `data.decision` (`approved`, `rejected`, or `needs-user`) and structured `data.issues` fields. Semantic control validation runs before output staging, artifact materialization, resource completion, or coordination settlement; an invalid result keeps external claims nonterminal for bounded retry. The result returns a Graph run id, not a JobRuntime id: the controller waits for the logged completion follow-up and never sends that id to `job_output`. Coordination failures before child creation are stored as bounded run-level errors and cancel remaining nonterminal nodes.

All deterministic operator changes enter one serialized control service. A request addresses the exact graph, immutable revision, run generation, and optional latest attempt, while the Host supplies the authenticated actor and ingress. Reusing an operation id with different input and targeting stale browser state both fail before mutation. Accepted records retain the request, actor, source, result, and resulting generation or revision. Supported operations pause admission at a durable human checkpoint, persist a node-specific task modification and ask the controller for the next immutable revision, approve or reject a checkpoint, cancel a run or node, retry, resume from a node, skip a declared skippable node, apply a generation-local assignment override, provide schema-valid substitute output with visible provenance, clone a historical revision as a new head, and request recovery reconciliation. A modification never mutates historical work: its checkpoint resolves only when the controller submits the replacement revision. Modifying an active node requests coordination cancellation and stops its Worker before the run exposes `awaiting_user`, so obsolete work cannot start another internal attempt. That path emits only the dedicated modification follow-up; it suppresses the scheduler's generic planning follow-up for the same checkpoint. Pause instead drains active attempts before exposing `awaiting_user`; approval starts one new generation and preserves only accepted predecessors. Manual reconciliation accepts a queued, running, paused, or awaiting-user run, returns a no-op while this Host still owns a live executor, and otherwise attempts fenced recovery of only the addressed run.

Every claimed node publishes bounded admission and schema-valid output progress, renews its fenced lease, and watches ordered external progress or cancellation after the latest cursor. Public-safe observations are retained as `progress` operation transitions; raw coordination state never enters a worker prompt after claim. Stopping the heartbeat loop drains a renewal that has already started, and Graph observes the claim before progress, cancellation, or settlement so a same-claim nondecreasing lease identity replaces its recorded value before the write. Every claimed node then writes one terminal coordination outcome under its Generation-scoped Activation. Cancellation and revision replacement request LoopX cancellation before stopping child work and do not cancel compensating writeback. Startup recovery first reconciles the prior Worker, then converts a still-running coordination claim to a terminal canceled settlement before an idempotent node runs under a new fenced Generation and Activation. A confirmed cancellation-request record alone never proves that the coordination lease was released. External settlements use one stable identity and append numbered attempts; `failed` and `conflict` attempts may retry after recovery, while `confirmed` is immutable. A terminal writeback failure after valid output is staged moves the run to an `awaiting_user` reconciliation checkpoint; recovery retries that Settlement before applying the attempt limit and never reruns the Worker merely to repeat writeback. Cleanup signals are bounded; an operation that cannot settle retains pending evidence for later recovery instead of blocking teardown indefinitely.

Admission is FIFO and simultaneously enforces the worker share of the global cap, role cap, exact provider/model cap, and optional model weight budget. One or more global permits remain reserved for the controller. The controller role's prompt, provider, model, and reasoning selection route the parent request while Graph Mode is active; worker selections are passed to each child. Worker caps reduce OOM probability, while each parent session already serializes controller requests. Deployments requiring a cap shared by controllers in different sessions or hard memory isolation must also enforce it in the model provider or process runtime.

Every accepted node stores a complete execution budget: `maxOutputTokens`, `maxReasoningOnlyTokens`, `firstDurableActionMs`, `maxNoDurableProgressMs`, `checkpointIntervalMs`, `maxWallTimeMs`, and `maxContinuations`. The four millisecond fields cannot exceed `2_147_483_647`, so a configuration cannot be clamped to an immediate Node timer or rejected by `AbortSignal.timeout`. Before admission, Graph Mode resolves the exact provider/model through `ctx.llm`, rejects an unsupported explicit reasoning effort, intersects the node output ceiling with the adapter and live resource ceilings, and records the context window, supported efforts, effective output cap, parallel limit, weight limit, and available device memory on the attempt. The local Worker passes the effective output ceiling into the child request. Graph Mode separately tracks provider-reported input, output, and reasoning usage, estimated streamed reasoning, model activity, and durable progress from child session events. Successful file mutations and successful focused verification commands create structured checkpoints with stable work and attempt ids, activation, content hashes, verification exit codes, remaining criteria, and next action; verification summaries retain the latest 2,000 characters after surrounding whitespace is removed. A failed verification neither creates a checkpoint nor resets the progress watchdog. The accepted structured result closes the checkpoint with completed criteria. Hidden reasoning alone never advances durable progress. Artifact-producing assignments must perform a durable action early. On Windows, an assignment that encounters the documented sandbox `spawn EPERM` process-I/O limitation is instructed to retry the exact command once with narrow sandbox escalation instead of modifying dependencies, caches, or build tools.

A token-limited or watchdog-stopped activation continues the same logical attempt only when it has a durable checkpoint, and the continuation receives that checkpoint rather than hidden reasoning or an unbounded transcript. A stop without a checkpoint, exhausted continuation count, or node wall-time exhaustion prevents same-granularity retry and opens a planning checkpoint. A Worker may also mark a deterministic failure as non-retryable; Graph records the Provider's exact code, consumes no further node attempt, and opens a planning checkpoint that requires corrected task or workspace ownership. The controller follow-up resolves each pending node's actual model profile and live capacity in addition to completed evidence, Worker, workspace, execution budget, health, latest checkpoint, and latest error. When a pending node has an accepted result in an earlier revision, the follow-up also includes the accepted revision, semantic node definition, incoming dependencies, output, and artifacts. The controller must preserve still-valid accepted nodes unchanged so Graph Mode can reuse them, rather than scheduling preservation or baseline-discovery work. The controller policy requires post-architecture implementation nodes sized for roughly 10–30 minutes, two to four measurable criteria, disjoint ownership for parallel work, independent artifacts, and a separate integration node instead of approving unchanged stalled or non-retryable work.

The Web composition dispatches Graph nodes in `isolated-copy` workspaces. Every assignment tells the model its exact mode plus source-relative read and write roots, treats objective paths as descriptive rather than writable locations, and forbids absolute source-workspace writes. The local Worker caps an in-process isolated child's sandbox authority at `workspace-write`, so a main session switched to `danger-full-access` cannot escape the allocation. Each successful isolated attempt stores a complete content-addressed artifact manifest with the source hash of every changed file, then materializes that manifest into the session workspace before the node can succeed. Every successor also reconciles all transitive upstream manifests before its Worker allocation, so recovery from an older run cannot dispatch against an empty or stale source workspace. Graph Mode rejects missing base evidence, divergent changes to the same path, unsupported symlinks, or source files that changed since allocation. Already-present content is not rewritten. Every actual materialization has a stable `artifact` Settlement. Integration nodes remain the explicit owners of cross-node conflict resolution, verification, and deletion; isolated deletion is rejected and is never inferred from an absent file.

The execution view displays the actual model and resource profile, effective budget, provider usage, estimated reasoning, last model activity, last durable progress, changed-file count, checkpoints, child sessions, output, and Settlement evidence. Operators can stop active work, return a node to the controller for a revised graph, resume from a checkpoint, retry or skip eligible work, switch role/model/Worker/reasoning effort, and replace the node output or reasoning-only budgets for the new execution generation. Exact models without advertised reasoning metadata disable the reasoning input.

When `schedulerProvider` is configured, Graph Mode acquires one whole-run lease before publishing every initial, recovered, or control-created generation, heartbeats it while the DAG advances, and releases it after the run stops. The lease fencing token becomes `ownerEpoch`; a Provider response below the requested epoch is rejected, and a busy live owner prevents a second Host from advancing the same run. Losing a heartbeat aborts Worker activity and immediately revokes Graph write authority: the old Host cannot append a canceled run, node transition, checkpoint, settlement, or completion follow-up. The last durable state remains nonterminal so a higher fenced generation can reconcile it. A per-agent recovery scan checks pending submissions plus queued or running durable runs that have no local executor; it attempts ownership after `recoveryScanIntervalMs`, treats a live remote lease as busy, and starts a new reconciled Generation only after acquisition succeeds. A `reconcile` node with no Worker reference is safe to redispatch because no model-controlled effect began; once a Worker reference exists, Provider reconciliation evidence remains mandatory. Graph reads use the eagerly maintained session projection when that capability is composed and fall back to full replay otherwise, so scheduler heartbeats do not compete with repeated folds of a large session log. Run projection also rejects a stale generation, a same-epoch takeover, a generation jump, or replacement of an accepted terminal snapshot. `schedulerHeartbeatMs` bounds renewal frequency. The Web profile uses the SQLite scheduler Provider for processes sharing its session directory.

After scheduler execution drains, every control path that pauses, cancels, retries, resumes, or replaces a Revision terminally settles claims retained by earlier failed attempts before replacement work can acquire overlapping scopes. A previously confirmed terminal coordination settlement is left unchanged.

## Model Experience

### Controller policy

#### What the model sees

The controller receives its configured role prompt, the active graph identity, enabled role catalog, deployment-authorized environment capabilities, and instructions to classify each human input before it creates, revises, inspects, or directly answers work through `graph_submit`. The tool schema asks only for semantic graph content; the Host derives graph identity, revision lineage, structural changes, and deployment fields. The controller must preserve explicit user requirements, locked baselines, and acceptance criteria, ask the user when they cannot be met as written, place necessary host prerequisites before their dependent engineering nodes, and place browser verification after an integrated runnable Web build. A `control` classification records intent but does not claim that a Graph control action occurred. Its configured provider, model, and reasoning effort route the active parent request.

#### Token effect

One bounded policy block and the configured role catalog are added to every active controller request.

#### KV Cache effect

The policy and unchanged role catalog form a reusable prefix; graph identity and the newest user input vary between turns.

### Node assignment

#### What the model sees

Each child sees its configured role prompt, one node objective, acceptance criteria, published predecessor outputs, and a compact coordination observation. It returns a structured summary, data object, artifact list, and optional public-safe coordination summary. A browser tester uses the inherited Chrome tools; screenshots enter its durable child log as image attachments, while page, console, and network observations remain detailed child evidence and its schema-valid decision returns to the parent run.

#### Token effect

Each attempt creates one child request whose variable size is the node description plus selected predecessor outputs and the provider-bounded coordination observation.

#### KV Cache effect

Role prompts can reuse a prefix among children with the same role and model, but node objectives, dependency outputs, and observations vary per attempt.

## Known Limitations and Deferred Work

- Recovery can replay staged settlements, retry failed settlement attempts, reconcile Worker/workspace and model-reservation references, cancel still-claimed LoopX work, and resume absent idempotent work. It cannot prove arbitrary external effects; manual, quarantined, conflicting, or unknown outcomes stop in `awaiting_user` until a precise control operation resolves them.
- The Web composition's SQLite scheduler and resource Providers coordinate local Host processes sharing one session directory, and its artifact Provider persists manifests on that filesystem. Artifact integration currently supports regular files with optimistic source hashes; symlink materialization and isolated deletion require an explicit integration implementation. Independent Hosts still require an authenticated distributed scheduler Provider, durable Worker identity and health, remote telemetry, authenticated artifact transport, and reference-aware orphan cleanup.
