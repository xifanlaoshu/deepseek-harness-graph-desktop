# Agent Note: Session Graph Mode

Status: implemented

English | [中文](2026-08-17-session-graph-mode.zh.md)

## Problem

One controller turn can delegate independent children, but a conversation has no durable representation for a changing dependency graph. The parent must remember which results feed later work, which tasks can run together, and which completed work is stale after the user adjusts an earlier requirement. This also leaves model-specific concurrency implicit, so a valid fan-out can overload a local provider even when every child is individually bounded.

The [dynamic workflow decision](2026-07-05-dynamic-workflows.md) solves model-authored, one-call script orchestration. Its JavaScript body and foreground run are the wrong ownership model for a conversation mode whose graph must remain editable, inspectable, and replayable across user turns.

## Decision

Graph Mode is a session-owned plugin family under `packages/graph/`. `dsh-graph` owns versioned configuration, immutable graph revisions, whole-run snapshots, validation, downstream invalidation, and the `graph` projection. `dsh-graph-mode` owns `/graph`, the controller policy, `graph_submit`, exact-command environment checkpoints, and the background scheduler. `dsh-graph-worker` defines fenced assignments for named local or remote Worker Providers, and `dsh-graph-resources` defines optional expiring observations and reservations below static limits. `dsh-client-ui-graph` renders the projection and sends validated whole-configuration replacements through the command channel.

Exactly one enabled role is the controller. While Graph Mode is active, its system policy requires classification of every human input as new work, a revision, inspection, control, clarification, or a direct response. The controller submits semantic tasks and dependencies without graph or revision identity. Graph Mode derives a safe collision-free id for new work, assigns revision identity and lineage from the session projection, discards Host-owned identity hints, and derives directly changed nodes from immutable structures. New work starts at revision one; an adjustment creates the next revision of the current graph and reruns the complete transitive successor closure of the derived changes. Successful nodes outside the closure are reused only with `reusedFrom` provenance; old revisions and runs are never rewritten. A planning checkpoint exposes accepted results from earlier revisions when their node ids reappear as pending, including the accepted semantic definition and incoming dependencies. The controller must preserve still-valid accepted nodes unchanged and plan only the missing work and verification; renaming accepted work as preservation or baseline discovery would invalidate reuse without new evidence.

An ordered long objective uses a Campaign above independent Batch Graphs. The first Batch submission carries the initial ordered plan and binds exactly to its first listed Batch; after the completion follow-up, each later submission omits that plan and binds only the named next Batch. Registered Batch definitions form an immutable prefix. The [append-only Campaign plan decision](2026-08-24-append-only-campaign-plan-revisions.md) permits one audited suffix after every registered Batch is accepted, without changing existing definitions or executions. Every Batch receives its own Graph id and stores only that batch's nodes, Revisions, and Runs. Campaign events retain dependencies, status, execution summaries, and confirmed Settlement ids. An approved Batch activates the next ready Batch through a controller follow-up, while rejection or execution failure creates Revisions only in the current Batch Graph. Replacement admission waits for the preceding Run to become quiescent, then reads the accepted Campaign projection again so every settled execution is retained exactly before the new execution is appended. Already approved Batch Graphs remain unchanged and are consumed through compact durable evidence rather than copied nodes.

Graph edges are data. Required edges impose completion order, while conditional edges evaluate `exists`, `truthy`, `equals`, or `not-equals` over a predecessor's published JSON. Every incoming conditional edge must be active before a node runs. Executable predicates and cycles are rejected before the revision reaches the session log. Each child publishes a schema-constrained summary, JSON data, and artifact paths. Its messages and tool events stay in the child session named by the attempt record.

Admission happens before external claim or child creation. One FIFO controller simultaneously enforces the worker share of a global cap, each role's cap, an exact provider/model cap, an optional weighted model cap, and `maxActiveSubagents`, the run-scoped total of live Graph Workers and their in-process descendants. `controllerReserve` removes permits from the worker share so fan-out cannot consume the controller's configured capacity. Top-level Workers wait in the FIFO queue, while a nested in-process start that would exceed the shared total fails with `CAPACITY_EXHAUSTED`; waiting while its parent holds a permit could deadlock at a limit of one. The capacity scope and ceiling travel through child `AgentOptions`, cannot be widened by descendants, and are retained in continuable descriptors for cold resume. A role's provider, model, reasoning effort, prompt, and cap are durable user-editable settings. While Graph Mode is active, the controller role overrides parent prompt assembly and the `agent/request` route; worker selections become child `AgentOptions`. The initial reasoning effort is also an `AgentOptions` input and is inherited by children.

Host prerequisites are immutable `environment` nodes governed by the [environment-operation decision](2026-08-22-graph-environment-operations.md). They isolate exact approved Shell commands from ordinary model Worker authority and place their completion before dependent engineering nodes.

External coordination is a replaceable seam rather than scheduler state. `dsh-graph-coordination` defines prepare, claim, heartbeat, observe/watch, progress, cancellation, settlement, and reconciliation. `dsh-graph-coordination-loopx` verifies an existing LoopX goal and role-to-peer mappings during prepare. Once a node becomes ready and passes admission, claim lazily creates or rediscovers its Graph-tagged todo, claims it with the role's registered peer, and returns a fenced lease plus compact observation. A controller may declare relative workspace ownership but never physical allocation ids or absolute paths. Draft admission resolves omitted read roots and cleanup policy, and rejects malformed roots with an exact field path before durable revision validation. Concurrent mutating controller nodes must declare disjoint write roots before admission. LoopX expands each precise root to cover its descendants, uses the deployment `writeScopes` only for unspecified or whole-workspace ownership, and assigns read-only Activations non-overlapping private scopes. Success completes the todo without a follow-up; terminal failure converts it to a blocker. Harness remains authoritative for execution and transcripts. The default Web bundle ships the provider row disabled because a goal id and peer identities belong to the deployment; enabling it fails loud if LoopX or its bindings are unavailable.

LoopX CLI response collection is deployment-configurable through `stdoutMaxBytes` and `stderrMaxBytes`. The stdout default accommodates multi-hundred-item goal registries, and the Provider distinguishes a truncated collection from malformed JSON so registry growth cannot turn a valid `todo list` into a misleading parse failure.

Graph persists stable logical Work, Generation-scoped Activation, operation, submission, settlement, checkpoint, and control ids. `graph/submission` is flushed before Scheduler acquisition or coordination preparation, and a Revision becomes current only with an owned queued Run. Resource reservation, coordination claim, running attempt, Worker dispatch, staged output, artifact integration, cancellation, and settlement each follow a persisted intent or accepted reference. A Scheduler lease has one explicit handoff to its background execution. Failure before that handoff releases the lease; failure after local admission but before Worker dispatch terminally settles an acquired coordination claim, releases an acquired model reservation, and returns the local permit. LoopX clears a soft todo claim and marks it blocked if its hard lease acquisition fails. Before dispatch, Graph resolves exact model capability and live resource profile, clamps the node budget, and stores both on the attempt. Recovery raises the owner epoch, reconciles Worker and resource references, repeats staged settlements under stable ids, and gives every new Generation a distinct coordination Activation while retaining the logical Work id for lineage. Each live Agent scans for durable nonterminal work without a local executor and attempts fenced reacquisition; a busy lease leaves the run unchanged for a later scan. A `reconcile` node without a Worker reference is redispatchable because no model-controlled effect began; a referenced Worker still requires reconciliation evidence. The controller and scheduler read the eagerly maintained graph projection when the projection registry is composed, avoiding repeated full-log replay in heartbeat-sensitive paths. Manual, conflicting, unknown, or failed cleanup remains in `awaiting_user`.

Local isolated-copy workers enforce declared write roots and publish bounded content-addressed mutation manifests. Every assignment makes the resolved mode and relative read and write roots model-visible. An in-process isolated child receives a `workspace-write` sandbox cap, and a read-only snapshot receives a `read-only` cap, so parent permission changes cannot authorize escape from the allocation. Every changed regular file includes the source hash from the copied workspace, while dependency and package-manager cache directory names are excluded at every depth during copying and capture. An allocation that fails validation or child startup before publication is always deleted. Deletion and undeclared-write results are non-retryable: Graph preserves the exact error, opens a planning checkpoint after the first attempt, and requires the controller to correct task or workspace ownership before replacement work. The Web profile uses isolated copies by default. Graph Mode validates and materializes every completed manifest through its Provider under a stable Artifact Settlement before publishing node success. Before any successor allocation, it also reconciles transitive upstream manifests, which restores accepted files from runs that predate progressive publication. Already-present content is not rewritten. Divergent same-path edits and source drift fail before writing. A distinct Integration node owns cross-node conflict resolution, verification, and deletion; isolated deletions and symlink integration fail explicitly instead of being inferred or overwritten.

Terminal coordination settlement has a lifetime independent from the Worker cancellation signal. Stopping a coordination heartbeat drains any renewal already submitted, and every progress, cancellation, or terminal write first observes the current Claim and accepts only the same Claim with a nondecreasing lease identity. A confirmed cancellation request is not a terminal result and does not authorize replacement work. Every live cancellation persists its settlement intent, requests cooperative cancellation, stops the Worker, and retains terminal evidence for reconciliation. An active task-modification control uses that cancellation path before entering `awaiting_user`, preventing the invalidated node from starting another internal attempt; a run pause instead drains the current attempt. A task modification emits only its dedicated controller follow-up and suppresses the scheduler's generic planning follow-up for the same checkpoint. A Run publishes its terminal snapshot only after all active node attempts finish cancellation and bounded external cleanup, then closes that scheduler execution's node-update path so delayed Worker-monitor callbacks cannot reopen the Run. Revision replacement therefore receives one quiescent predecessor snapshot. Same-Revision retry keeps the logical Work id but receives another Activation, so an immutable terminal Todo never blocks a later Generation. Control-node result validation precedes output staging, artifact materialization, resource completion, and terminal coordination settlement; a schema-valid but semantically invalid result therefore leaves the Claim nonterminal for a bounded retry within the current Activation. A writeback failure after output staging creates an `awaiting_user` reconciliation checkpoint; recovery retries the stable Settlement before attempt exhaustion and does not rerun the Worker. External cleanup uses configured deadlines and caller-side abort races; a Provider that ignores its signal cannot block teardown indefinitely, and unfinished cleanup retains recoverable pending evidence.

The Web bundle mounts the graph domain, Worker and resource Service Definitions, local Worker Provider, controller, and `ui-graph`. The session-header button exists only while the projection is active. Its horizontal panel separates immutable design from actual execution records and shows revision selection, conditional edges, node phase/output/artifacts/attempts, effective Worker/model/reasoning route and capacity, exact token counters, last model activity, last durable progress, workspaces, waits, LoopX claim ids, checkpoints, Settlements, and links to authoritative child sessions. Operators may stop active work, return a node to the controller, resume from a checkpoint, and restart a node plus its successors with a different role, model, reasoning effort, Worker, output ceiling, or reasoning-only ceiling. The settings tab keeps a disposable working draft while it is open, so unrelated run projections cannot replace user edits. Its save action remains outside the scrolling role list, reports command-level rejection, and replaces session configuration through `/graph config <JSON>` for Host validation and append. The model dropdown reads the shared settings-backed model directory. A selected model accepts only its advertised reasoning efforts; the editor blocks an unsupported role value and keeps a stale value editable until the user clears or replaces it. Models without advertised reasoning metadata disable an already-empty reasoning field. Only the logged projection is authoritative after the editor closes.

After scheduler execution drains, control operations that pause, cancel, retry, resume, or replace a Revision terminally settle claims retained by earlier failed attempts before replacement work acquires overlapping scopes. Confirmed terminal coordination settlements remain authoritative and are not canceled again.

The Pending Submission's original activation and startup recovery share one single-flight identity. Recovery cannot repeat Scheduler acquisition or coordination preparation while the submitting activation is still running, and execution cleanup removes only the promise that still owns the Run entry.

An Activation's accepted terminal state is idempotent at claim time. Memory and LoopX Providers return its outcome and evidence instead of claiming it again; LoopX checks the durable journal and current Todo state before invoking the CLI claim operation. Graph never dispatches a Worker from that terminal disposition and preserves a stable run-level coordination error when local durable evidence still requires reconciliation.

The Web UI places an ordered Campaign Batch track above the selected Graph. Each card opens one independent current or historical Batch Graph, so presentation preserves cross-Batch history without merging completed nodes into the active DAG or changing durable current-Graph state.

## Verification

Domain tests cover configuration, DAG rejection, controller-plan identity resolution, concurrent workspace admission, provisional submission replay, run replacement, invalidation, output reuse, timer ceilings, checkpoints, and artifacts. The tool-boundary case proves omitted or malformed graph-id hints receive a safe Host id, stale lineage, timestamp, and termination fields cannot override the current projection, and changed nodes are derived without controller hints. Workspace draft cases prove omitted read and cleanup defaults and exact diagnostics for malformed roots. Scheduler tests cover a failed durability barrier, Scheduler refusal without Head drift, pending-submission recovery, automatic orphan-run reacquisition, live-executor reconciliation as a no-op, same-Revision retry through `MemoryGraphCoordination`, non-retryable workspace failure returning to the controller after one attempt, an in-flight renewal completing while its Worker stops, replacement while two active Workers finish cancellation at different times, settlement-only recovery after the node attempt limit, and a control Generation settling a prior Attempt's retained Claim before reacquisition, in addition to admission, Worker, resource, artifact, cancellation, and recovery behavior. Projection coverage proves Graph Mode reads the live incremental state when the registry is composed. Local Worker tests cover sandbox caps, root-relative multi-segment exclusions, and dependency or cache directory names nested below package roots. LoopX tests cover Activation-keyed conformance, workspace-derived lease scopes, reconstructed-provider settlement from a durable Claim, CLI timeout, bounded response collection, journal-loss repair, and settlement concurrency across Activations. Client tests cover graph visibility, layout, controls, model and reasoning selection, timer validation, settings serialization, recovery controls, and teardown. The keyless headless snapshot mounts the shipped graph plugins, rejects an empty workspace root with its exact path, admits the corrected retry, and pins terminal DAG events plus final synthesis.

A real Web profile run validated the assembled path with LoopX enabled. A four-node graph ran one source node, started independent review and verification nodes one millisecond apart, and started the result node only after both conditional predecessors completed. The run finished `succeeded`, both conditions were present in the result data, all four child sessions and claims were retained, all four LoopX todos reached `done` with `--no-follow-up`, and the generated source and result files contained their exact expected markers. A separate one-node browser run also completed with no run-level or attempt-level error.

A browser revision run exercised cancellation compensation against the real LoopX CLI. Revision one claimed a node whose child was blocked in `sleep 30`; revision two replaced it while active. The first run and child ended with explicit parent cancellation, its claimed todo became a non-executable blocker, and the replacement created a distinct claim that reached `done` with `--no-follow-up`. The parent plus both complete child logs contained 362 parseable records across 194 complete Zstandard frames, no torn frame, tool failure, step failure, or unexpected error event. The replacement artifact contained the exact expected three bytes and the canceled artifact was absent.

Capacity tests cover concurrent pending starts, inherited ceilings, rejection of changed capacity, descriptor persistence, cold resume, top-level FIFO admission, and both settings editors. The keyless Graph snapshot pins the run configuration, controller policy, and Worker policy for the active-subagent ceiling.

## Alternatives considered

**Extend dynamic workflows.** A workflow script is immutable inside one tool call and intentionally allows general JavaScript. Adding cross-turn mutation, session revision semantics, and a permanent controller to it would conflate two useful products and inherit executable-condition risk in durable graph data.

**Teach the agent loop to dispatch graphs.** Rejected because command, prompt, tool, projection, subagent, and UI extension points already provide the behavior. Making the default driver graph-aware would turn an optional composition into privileged loop policy.

**Mutate one graph record in place.** Rejected because inspection could not distinguish original evidence from revised work, and a partial write could leave downstream results looking current. Immutable revisions plus explicit reuse make every answer attributable.

**Create and register LoopX goals automatically.** Rejected because a LoopX registry and peer identities are an external administrative authority. The Harness may add todos to the selected goal, but it must not silently invent deployment identities or redirect work to a new control plane.

**Queue an over-cap nested subagent start.** Rejected because a parent Worker remains live while it waits. At a ceiling of one, the child can never acquire the only permit until the waiting parent exits. Failing the nested start returns control to the Worker and then the controller, which can express the remaining work as sequential Graph nodes.

## Consequences

Graph Mode makes dependency-aware multi-agent work visible, revisable, recoverable, and independently routable without changing the loop, and concurrency becomes an enforceable admission decision instead of controller advice. The cost is additional submission, session, child-session, operation, and settlement records plus deployment configuration. Static caps lower OOM risk; a resource Provider is required to observe actual model-server or device state. A very small active-subagent ceiling requires the controller to decompose large work into dependency-ordered, model-sized nodes because recursive fan-out is rejected rather than queued. The in-process capacity scope does not become a distributed semaphore across remote Worker hosts. Recovery can retry terminal logical Work through a new Activation and settle staged LoopX output through the durable Claim Todo id, but it cannot prove arbitrary external effects without a Provider reconciliation API. Lazy Todo creation avoids speculative external work for canceled, skipped, or never-ready nodes. LoopX coordination is available only after a deployment supplies an existing Goal and complete role-to-Peer mappings.
